# 多麦克风工程开发文档

更新：2026-10-02。工程入口：`esp32_multi_mic_device.ino`。当前版本 2.0.0，已补齐单麦克风功能，以后作为主维护工程；单麦克风保留兼容维护。

## 文件夹用途

| 目录 | 用途 |
| --- | --- |
| 工程根目录 | Arduino 运行源码、头文件、引脚表、分区表、编译脚本和本机配置。打开同名 `.ino`，同级 `.cpp` 会参与编译 |
| `docs/` | 最新逐针接线、接线图及可再生成图的脚本；保留基础单麦克风接线和原功能参考 |
| `tests/` | 验证记录和测试入口。此目录不参与设备固件编译 |
| `tests/voice_capture_host/` | 在 Windows 上编译生产音频/麦克风配置代码，用模拟 I2S、NVS、文件系统、VAD、降噪验证逻辑；`freertos/` 子目录提供互斥锁模拟头文件 |
| `wake_models/` | 与固件匹配的 13 个中文离线唤醒模型包、模型说明 |
| `build/` | Arduino CLI 生成的应用镜像、bootloader、分区表、模型文件、编译缓存和选项；不要在这里编辑源码 |
| `build-host/` | Windows 主机测试可执行文件；不会烧录到 ESP32 |

`build/` 内的 `sketch/`、`core/`、`libraries/` 是编译器生成文件；其内容可以重建。实际引脚定义在根目录 `hardware_pins.h`。

## 数据流和兼容方式

```text
I2S0: MIC1 左 + MIC2 右 ─┐
                         ├─ 检查安装掩码 ─ 固定/auto选路 ─ 16kHz单声道
I2S1: MIC3 左（需要才开）─┘                              ├─ 降噪/VAD/录音上传
                                                        └─ 离线唤醒
原有播放数据 ─ I2S0 TX GPIO40 ─ MAX98357A
```

首次默认掩码 1。`count 1/2/3` 对应掩码 1/3/7；任意组合用 `mask`。未启用的 MIC2 不参与选择，未启用的 MIC3 不启动 I2S1。只有 MIC2 或 MIC3 时，I2S0 仍为原功放服务。

两组总线分别以 32bit 双声道时隙读入，MIC3 只取左槽。读取补足短包并核对帧长度，第二总线错误使本次录音失败，避免上传部分音频。取消录音、存储、NS/VAD 和内存 PCM 仍走原路径；硬件释放时关闭两组控制器，恢复时按当前配置重建。

两组读取帧数相等只表示缓冲消费数量相同，不意味着硬件采样同步。auto 选择整路，不做跨控制器相加；待机切换时重置高通状态，开始收音后冻结通道直到本次录音完成。录音准备清理缓冲时保留上一轮监听选择的通道，避免唤醒后又回到第一只。若未来实现阵列定位，需要重新设计共同采样时钟、同步、通道校准和算法。

## 日常开发顺序

1. 新增功能优先在此工程开发，单麦克风工程保留必要兼容与修复；发布前分别编译，不要混用两个 `.ino`。
2. 改引脚时同时更新集中引脚表、接线 Markdown 和 SVG。在 `docs/` 执行 `生成接线图.ps1` 可重建本目录的图。
3. 改采集、选择或配置后运行 `tests/voice_capture_host/run.ps1`，检查兼容路径及多路异常处理。
4. 执行 `build.ps1` 编译真实 ESP32 目标并核对离线模型。Arduino IDE 也须选择同样的 Flash、PSRAM、分区与 USB 选项。
5. 接线后先 `/mic count 1` 验证原单麦克风，逐步增加实际安装数量；固定通道分别检查，再使用 auto。

当前为独立开发版本，OTA 硬件通道 `esp32s3-cloud-voice-multimic-v1`，服务器发布需要单独配置。版本、硬件通道和模型验证必须一起核对，不能直接复用单麦克风发布包。

## 实机验收

先验证一只、两只、三只及任意组合；逐只固定录音确认左右槽和 MIC3 引脚。再检查按键录音、自动停顿、离线唤醒、功放播放、中断和硬件释放恢复。最后同时运行屏幕和舵机，检查电源、噪声、削波及 DMA 丢帧。

已做软件验证，尚未接线、烧录或执行这些实机步骤。构建通过也不表示实际板的供电、模块针序或采样同步已验证。
