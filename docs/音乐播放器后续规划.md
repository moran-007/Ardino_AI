# 音乐播放器后续规划（暂不实施）

用户范围：本次只交付音乐闹钟；完整播放器后续在多麦克风工程扩展，单麦克风保持兼容维护。当前 `music_player.cpp/.h` 是有限长度 PCM 闹钟循环模块，不应把它的整段缓存直接扩展为完整歌曲。

## 建议的顺序

1. 自有音乐库 + MP3 流式下载/解码 + 播放、暂停、继续、上一首、下一首 + 屏幕歌名和网页按钮。
2. 歌名/歌手搜索、歌单、收藏、睡眠定时、网络恢复和播放进度续播；按钮或机器人对话打断后按用户意图恢复音乐。云端返回曲名、歌手、时长、编码及可续传的媒体地址，维护稳定 track_id。
3. 高采样率音乐期间持续唤醒、回声消除、用户讲话自动压低音量，再独立实现多麦克风方向判断。

音乐源先用用户上传的自有文件，不依赖不稳定的第三方搜索/播放地址。云端保存原音频和统一编码的播放版本，未来管理员和设备网页均提供歌曲管理；不要沿用现在 15/30 秒的铃声限制承载完整歌曲。

## 音频时钟与唤醒

当前 MIC1/MIC2 与功放共用 BCLK42/WS41，MIC3 在第二个 I2S 控制器上独立采集。WakeNet 输入必须为 16 kHz 单声道有符号 16 位 PCM。直接把共享时钟切到 44.1 kHz 会改变麦克风采样率，不能继续把这些样本当作 16 kHz。

候选方案是统一为 48 kHz 采集/播放，麦克风经有抗混叠滤波的 3:1 降采样供 WakeNet/ASR；音乐必要时重采样到 48 kHz。48 kHz 是候选工程选择，尚未验证现有软件开销、DMA稳定性和实机音质。另一方案为调整接线分开 TX/RX 时钟，需要重新评估两组麦克风、I2S资源和 GPIO；不能未经验证承诺加一个独立第三控制器。

当前跨两个 I2S 控制器的数据没有相位同步，选响亮通道并非波束形成/方向辨别。后者需要另外验证同步与阵列标定，不能与本版麦克风输入检测混为一谈。

## 缓冲、调度与恢复

- 下载、解码、I2S播放分阶段推进，采用有上限的环形缓冲，不能随歌曲长度扩大内存。初期可测 64–128 KiB 压缩缓冲和小块 PCM；这是测量起点，不是已确认的资源预算。
- 音频硬件只有一个明确的输出拥有者。闹钟、按键/唤醒对话、TTS、提示音、音乐的抢占和恢复规则集中定义，避免各模块单独改时钟或抢喇叭。闹钟响铃时依然允许用户说停止/延后指令。
- 暂停保存曲目和解码位置；MP3续播需按帧边界处理，HTTP Range 可恢复下载，不等同于任意字节位置都能立即开始解码。
- 播放音频作为 AEC 参考；多麦克风并不自动消除喇叭回声。先测不同音量下唤醒和自触发率，再决定 DSP 与模型方案。

## 后续验收

连续播放 30 分钟、弱网/断网恢复、换曲/暂停与按钮响应、音乐与闹钟/TTS抢占、OTA前停止并释放资源、不同音量下唤醒/识别、PSRAM/内部RAM峰值、温度和供电噪声。目标是音频不争用、控制及时响应、断线可恢复，再评价音质。
